## 1. 目标与“全双工”的定义

目标是让双方自然、持续地交流，而不是“录完一条、上传一条、等完整 WAV 再播放”。通话中音频输入与输出应能独立持续，显示和记录各自状态。

验收需要分开衡量：

- **双向媒体**：播放爱莉声音时仍可采集用户声音，不靠关麦避免相互打断。
- **插话与让声**：用户可在输出期间开口；根据明确的交互策略停止旧播放、处理新输入，不能漏掉开头。
- **认知/工具并发**：后台工作期间是否仍能自然交谈，必须独立验证；不能以“双向传输已通”冒充认知层连续同时听说。

官方文档将 Realtime 单一语音模型、GPT-Live 配独立后台、以及可替换各阶段的串联链路分别描述。当前模型目标保持 Realtime Mini，不因“全双工”一词自动换成 GPT-Live，也不把现有 ASR→文字主意识→Breeze 标为 Realtime 原生语音到语音。参考 [R1]、[R2]、[R3]。

## 2. ElyHarn 当前基础与缺口

以 2026-11-12 只读盘点为起点；源码与需求要分别判断，后续变动需复核。

| 现有部分 | 可复用点 | 不能据此宣称已完成 |
|---|---|---|
| `conscious-mind/src/main-session.ts` | 原生 Agent、固定主 Session、create/resume 装配与工具权限 | Realtime 外部会话不是自动成为该 DSH Session |
| `conscious-mind/src/inbound.ts`、`pending.ts` | 来源、顺序与入站 owner | 目前是 text/image 批次，1.2 秒静默且等待整轮，不适合逐帧音频 |
| `conscious-mind/src/breeze-tts.ts` | 共享合成服务、独立取消、固定音色 | 当前完整 PCM/WAV 处理不是已经实现的实时双向媒体 |
| `dsh-livestream/src/stage/store.ts` | 真实播放进度、结束、失败、取消和超时回执 | 文件播放结束回执不能直接替代 WebRTC 的端到端播放证据 |
| Ayla 的 Web/Flutter LiveKit 媒体层 | 设备、AEC、降噪、音量和音频路由 | 现有人类语音房与旧 Voice Live 不代表 ElyHarn 已接通 AI 音频 |
| `subconscious`、`proactive-system` | 已有统一活动与机会输入的需求边界 | 仍为占位/需求，不能依赖尚未存在的运行服务 |

当前文字主 Session 的 id/cwd 与主体文件不得因新增语音功能被改名、清空、复制或自动迁移。语音需求不能要求当前 TUI 出现一个只有名字相同、实际不相连的新会话来假装接入。

## 3. 独立语音 Session 与 SOUL 已选

用户已选择独立的新语音 Session，系统仅使用现有 SOUL，并复用既有站立提示词管理。这取代先前“独立语音窗口或严格经文字主意识二选一”的待定状态。实际 Session 尚未创建，MVP 仍待审批。

保持同一持续主体，不另造语音人格或私有长期记忆。provider 会话、应用通话、DSH Session 和意识运行对象显式关联。文字主意识的 id/cwd、工具与私有历史不变；普通聊天输入继续原路径，不经过语音 Session。

- SOUL 通过既有 scoped standing-prompts 和完整 system prompt 装配读取；只选 SOUL，不复制或改写主体文件，不额外拼接系统/开发者人格提示。
- complete 配置不代替工具和 contexts 隔离；首版空工具为审批建议。
- 新语音 Agent 必须真正注册、驱动、记录和关闭；现有普通 agent factory 不能被旁路 Realtime 或同名空 Session 冒充。
- 媒体停播、模型响应取消和其他主意识工作保持独立；不写死语音对全部事项的语义优先级。
- 原生适配合法扩展点、SOUL每轮同步、私有上下文隔离和记录先经离线门槛；失败不先开付费通话。
- 详细 Session、媒体、权限、留存、预算及验收建议见 [PLAN-MVP.zh.md](PLAN-MVP.zh.md)，当前不注册实例。

## 4. 媒体与服务端结构（建议）

建议第一版 Web 一对一；Ayla 后续复用媒体设备层，另接 AI 媒体网关。不是本轮已批准的客户端决定。

候选链路：

```text
用户麦克风 ──音频输入──→ OpenAI Realtime Mini
                                │ 文字增量
                                ▼
                   Spark voice-call 与受控 TTS 入口
                                │ 稳定短句
                                ▼
                      官方 BreezeTTS2 流式 API
                                │ PCM 音频流
                                ▼
                      用户播放器与播放进度回执

控制与归属：Spark voice-call → 获准的意识入口与统一活动记录
```

Realtime 使用纯文字输出，不生成 OpenAI 声线。[R9] Breeze 官方已提供流式音频生成与 HTTP 服务，不能再把它记为需要我们重写的推理能力；按固定版本官方接口提交完整短段文字并流式消费 PCM。当前未见同一请求追加增量文字的接口。[B1][B2] 共享服务迁移已实施并通过聊天语音验收，见 [迁移验收记录](../../docs/report/2026-11-12-breeze-official-service-migration.zh.md)；通话消费路径仍待实施。

- 浏览器负责真实麦克风权限、设备选择、AEC/降噪、播放与静音；客户端麦克风在用户端，不是默认调用 Spark 的音频设备。
- Spark 负责用户鉴权、通话所有权、授权会话创建、固定模型与预算、工具执行及事件记录。
- 优先评估官方 WebRTC unified SDP 协商或短期 client secret，长期项目密钥不进浏览器；只选一种经审计的主协商路径，避免重复建会话。[R4]
- 服务端 sideband 可观察/控制同一 provider 会话，不能因为两端都收到事件而执行两次工具。[R5]
- 本地会话必须先准备好归属与记录，再启用生成输出；不把未登记输出静默补记成主意识活动。
- 音频帧不排进当前文字 pending，不积累成无限内存队列；媒体流、字幕、控制和持久记录各有背压与 owner。
- 不将音频接到 DSH 工具终端或在当前 TUI 里隐式开麦。
- 浏览器入口须符合安全上下文要求；公网部署需 HTTPS 与应用鉴权，服务端不得成为任意人消耗 key 的开放代理。网络可达性、ICE 与弱网另行验证，不保证部署即连通。

## 5. 用户操作与运行状态

打开界面、启动 ElyHarn、加载插件、建立通话和打开麦克风是不同动作。默认不因开机、进页面或加载插件而自动开麦/拨号。

界面未来应有明确的“开始通话、静音/取消静音、停止当前播放、挂断”和输入/输出设备选择；静音是停止发送输入、停播是本地输出控制，均不等于挂断。

工程状态按独立维度显示，不用一个互斥的“正在听/正在说”掩盖双工：

| 维度 | 必须能表达的事实 |
|---|---|
| 连接 | 未连接、协商中、已连接、重连中、已结束、失败或结果未知 |
| 采集 | 未授权、采集中、已静音、设备不可用 |
| 输出 | 未开始、播放中、被打断、已停止、拒播、设备失败 |
| 处理 | 空闲、生成中、工具工作中、失败或取消 |
| 归属 | 绑定的真实主体实例/Session，或明确尚未绑定 |
| 用量 | 已确认累计用量、预算状态，断线未结算则未知 |

“正在说”与“正在听”可同时出现。没有新字幕或没有新日志不等于进程停止；进程存活、连接正常与任务成功也不互相等价。后台关闭或归属丢失时，界面不得继续宣称爱莉在线。

## 6. 插话、VAD 与实际播放

- 评估 `server_vad` 和 `semantic_vad`，参数可配置；默认模式与策略待试验，不用 VAD 判断情绪、意图或话题重要性。[R6]
- 插话发生时按所选策略停止旧播放、清理队列并处理 provider 响应，防止旧音频晚到继续说。
- 采用 Realtime 纯文字加外部 Breeze 音频后，不能照搬 OpenAI 原生音频的自动截断。播放、TTS 取消及已播范围由应用记录，维护后续对话投影；不得把 `conversation.item.truncate` 当作外部 TTS 文本截断接口。[R3][R9]
- 记录生成、传输、播放和确认各阶段。服务端输出缓冲排空不等于物理扬声器已播放，也不能证明用户实际听见。
- 保留可证明的播放器进度与测量误差；无法观察的区间记为未知，不编造精确听取时间。
- 对话投影可撤下未播部分以免后续模型误认为用户已听见，但原始生成、被中断片段及事件历史保留，不通过删日志“修复”历史。
- 迟到音频和工具结果携带具体 call/response/item 与 generation/epoch，旧代内容不得自动播入新通话。
- 误触发、外放回声、咳嗽、笑声、长停顿、中英切换、名字和数字都要实测；不承诺调低一个阈值就解决所有打断问题。

## 7. 工具、权限与后台工作

- 所有外部副作用经服务器授权并明确唯一执行 owner；客户端不持工具凭据。
- 工具事件去重保留 invocation 与实际结果，不靠“再次收到”自动重发。
- 断线、用户插话或挂断时，逐项确定哪些媒体/生成应取消、哪些已授权后台工作可以继续。已完成副作用不假装回滚；状态未知不自动重做。
- 口头确认必须匹配真实执行结果，不能在工具仅排队时说已经完成。
- 先只实现已批准的工具清单和预算，不因模型支持 function calling 就开放主意识全部工具。
- 不用关键词分类或默认思考文本补造爱莉的内心字段，不把 provider 不提供的隐藏推理伪造成完整意识记录。

## 8. 音色与 Breeze 服务

输出方案已由用户选定为 BreezeTTS2。现有默认爱莉参考音频、对应参考文字与主体提示词内容不动，不上传至 OpenAI，不以云端音色或 Voice Design 替代既有参考声音。

共享服务已使用固定上游版本的官方推理及 Streaming API，不保留我们对模型推理、采样或 codec 的自定义改写；有界排队与协议兼容位于独立无模型接入层。旧本地 fork 已停止并保留作显式回滚，默认参考音频未改。实际部署、聊天语音验收与回滚边界见 [迁移验收记录](../../docs/report/2026-11-12-breeze-official-service-migration.zh.md)及 [操作说明](../../docs/operations/breeze-official-service.zh.md)。

官方输出是流式 PCM；现有聊天与直播客户端收全后封装 WAV 是文件消息行为，应保留。未来通话另增流式消费接口，不修改现有完整音频返回契约。并发调度放在官方推理层之外，保留有界队列、取消和独占清理要求。[B1][B2]

Realtime 只提交实际要说的话及明确的表达控制，不朗读隐藏推理。Breeze 的 instruction、Voice Direction 和内联 vocal events 可在固定参考音色下使用；模型不获得参考音频替换参数，不由基础设施按关键词自动选择情绪。短句切分、段间韵律、排队延迟和外部音频打断需独立验收。

共享服务迁移任务已真实合成、由爱莉调用原工具投递语音，并得到用户播放和音色正常的反馈；没有训练或上传素材。通话占位本身仍不采集、生成或播放音频，下一步才是 Realtime 通话。

## 9. 安全、隐私与活动记录

- 长期 key 仅从受控服务端凭据取得，接口只接受授权会话参数，不接受浏览器指定任意 model/baseURL 绕过策略。
- 所有会话控制、事件订阅与媒体资源访问验证当前用户和准确 call owner，不能只凭客户端传来的 call id 放行。
- 关闭通话须释放本通话麦克风、播放器、连接、监听与临时凭据；不能停止共享 Breeze 或其他通话的媒体。
- 身份、实例、源事件、occurrence、版本与因果链按主仓规则保留；语音活动不能成为只有插件自己看得见的第二本长期账。
- 用户原声、转写、原始生成内容、外显说话、工具与播放结果保持来源区分；字幕可能有错误，不冒充逐字无误的原声或已听事实。
- 必要权威活动留存与额外“整通诊断录音”分开设计；不能因为默认不作诊断录音就丢弃已经生成的主体活动，也不能借完整记录无限保存用户的环境声音。
- 原始音频是否留存、授权方式、保存时长、访问/导出/删除政策及与不可变权威记录的边界尚待确认。确定前不启用生产采集。候选原则是只持久化明确授权的媒体，以受保护引用关联，原文不进公共日志。
- 不在普通日志、URL query、用量面板或错误栈里泄露 key/token、SDP 敏感字段和私人正文；诊断默认只显示必要阶段、ID 与错误码。
- 任何网络中断导致的记录缺口、结束回执缺失与预算未知必须可见；不补造“已完整归档”。

## 10. 长通话、关闭与费用

- Realtime provider 会话与本地持久 Session 生命周期不同，不承诺挂断后同一 provider id 可以恢复；重连前明确是恢复连接还是创建新 provider 会话。
- 官方 Realtime 当前单会话时长上限为 60 分钟；需设计续接、上下文授权重建和记录衔接，不能简单拼造一段“记忆摘要”。[R3]
- 重试有明确上限、退避、epoch 与所有权。浏览器刷新、重复点击拨号和重连不产生重复计费通话或重复表达。
- 挂断立即停止本地采集和播放；服务端继续有限时间完成已授权的清理、取消与用量结算。清理失败和强制结束单独记录，不因此永远占着麦克风。
- 主动挂断、页面关闭、设备拔出、服务关闭与异常退出均须验证；不能用后台无限重启维持一个界面上已结束的通话。
- 按实际 token usage、缓存、工具和额外转写计费分别统计；价格从当期官方页面复核，不把音频 token 单价直接称为固定每分钟通话价。[R8]
- 并发数、单通话时长、会话创建速率、用量/金额上限和超限动作待确认。失联与结算缺失记为未知，不能算零费用。
- 达到明确工程预算时可阻止新付费请求或终止连接并告知用户，不替她决定事项语义上已经结束，也不静默换贵模型或改用其他云渠道。

## 11. 通话实施阶段（待后续授权）

- **阶段 0，当前**：无行为占位、需求草案、轻量生命周期测试；不启用任何入口。
- **前置阶段，Breeze 共享服务已迁移**：官方推理及原 `send_voice` 的真实投递、用户播放和音色已验收，默认参考音频不变。直播和旧 Python 做契约复核，未另外触发真实终端；不能据此声称通话已实施。
- **阶段 A，离线原生适配门槛**：先用假 Realtime 验证真实独立 Agent/Session、SOUL-only、合法活动记录、单一 owner 和关闭；未通过不拨付费通话。
- **阶段 B，媒体小样**：按审批的首发 Web 方案，以假音频验证宿主认证流式载体、PCM 播放器、权限与 WebRTC；不先旁路运行另一个语音人格。
- **阶段 C，受控真实短测**：凭据与留存授权明确后，Mini 音频输入/文字输出接 Breeze 流式播放，验证每轮 SOUL、字幕、插话、静音、挂断和费用；首版空工具。
- **阶段 D，端到端验收**：真实设备听测、取消/关闭/账本证据和原聊天 send_voice 回归，之后才允许启用入口。

首版执行严格以 [PLAN-MVP.zh.md 第9节](PLAN-MVP.zh.md#9-审批后的实施顺序) 的待审批顺序为准：先离线真实归属，再媒体，再付费短测，不能沿用“先旁路通话、后补意识接入”的旧顺序。每阶段区分源码完成、离线测试和真实验收，不以 UI 能打开代替可用。
