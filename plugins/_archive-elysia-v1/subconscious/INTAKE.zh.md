# 潜意识信息收集与 Router 接收设计

状态：**接收线设计已审定并完成最小实现；第 13 节列明已验证范围，真实来源适配与专业派工仍待后续建设。**

本文只讨论一条链路：**收集什么、收集多少、如何管理收集来的信息，以及如何把这些信息可靠地传递给潜意识中枢 Router。**

任务派发、专业潜意识执行、主动机会呈现、记忆文件格式和 Router 的最终路由工具 Schema 不在本文展开。本文保留 `RouterBatch`，但重新限定它的职责：批次是 Router 一次有界阅读与研判的单位，不是观察数据的寿命、读取权限或唯一投递协议。

## 1. 目标与原则

### 1.1 目标

1. **完整接收**：声明范围内的表界信息都有不可变、可追溯的观察记录，不按关键词、重要性或情绪预先筛选。
2. **多来源可扩展**：主意识 Session、QQ、KOOK、飞书、邮件及未来来源使用同一套观察与接收契约，不为每个来源重写 Router。
3. **全量保存，有界呈现**：权威内容完整保留；单次交给模型的材料可以有大小限制，但节选必须显式标记并可续读。
4. **有序但不伪造因果**：同一来源保持顺序；跨来源只承诺宿主接收顺序，不凭时间戳伪造真实因果。
5. **接收与研判解耦**：收到、成批、进入 Session、进入模型请求、作出决定是不同事实。
6. **不阻塞主意识**：潜意识存储、模型、休息或队列故障不得卡住主意识现有接收与回复。
7. **有迹可循**：每条观察、每次投递和每个后续任务都能回到稳定来源及真实形成过程。

### 1.2 核心边界

> **Observation 管“发生过什么”；Batch 管“这一次看哪些”；Delivery 管“是否真的送到”；Decision 管“这次研判产生了什么”。**

四者可以互相引用，但不能合并成一条含义模糊的状态。

## 2. 总体链路

```text
主意识 Session / 外部平台 / 邮件 / 未来来源
        │
        ▼
Source 适配器
  识别来源、稳定去重、确定 Thread、保留原始引用
        │
        ▼
SurfaceObservation 权威存储
  不可变、可恢复、可续读、带权限边界
        │
        ▼
待研判队列
  仅表示“尚未获得一次有效 Router 研判”
        │
        ▼
RouterBatch
  从待研判材料形成不可变、有界、有序的本次视图
        │
        ▼
持久化投递记录
        │
        ▼
Router Session 的真实用户消息
        │
        ▼
模型呈现证据 → Router Decision
```

任何阶段失败都不能靠推进游标或修改文案伪装成下一阶段已经完成。

## 3. 收集范围

### 3.1 进入主意识的信息

声明范围内应包括：

- 用户文字、图片、语音、文件和平台事件。
- 实际交给主意识的工具结果、计划提醒、主动机会及其他内部输入。
- 消息的来源、渠道、会话、作者、来源消息 ID、发生时间和可用的回复关系。
- 主意识实际获得的是正文、附件本体、附件元信息，还是某种经过裁剪的投影。

“平台已经产生一条消息”不等于“主意识已经收到”；采集记录必须能说明信息跨到了哪一层。

### 3.2 主意识产生的表界活动

声明范围内应包括：

- 可见 assistant 正文。
- `send_text`、`send_voice`、文件操作等真实工具调用与结果。
- `pass`。
- 主意识亲自提交且真实记录的 `thought`、`mood`、`decision`、`expected_response`。
- 后续平台回执，例如实际发送成功、失败或平台消息 ID。

原始表达、工具调用和平台回执是不同事实，应通过关联引用连接，不应合并成一条无法区分来源的记录。

### 3.3 不进入表界观察流的内容

- Router 和专业潜意识自己的内部活动，避免把内部处理递归伪装成新的外界输入。
- 凭据、Token、密钥及与表界理解无关的部署秘密。
- 纯框架运行上下文；必要时保留诊断引用，但不冒充用户输入或主意识主体表达。
- provider 没有暴露的隐藏推理。只能采集真实存在且获准投影的记录，不能补写或猜测。

### 3.4 工程过滤与语义筛选

采集层可以执行明确、可审计的工程规则，例如：

- 丢弃渠道对自己 bot 消息的重复回声，但保留原始表达与回执的关联。
- 排除框架心跳、固定提示词注入等不属于表界经历的事件。
- 拒绝无法通过基本结构校验的来源事件。

这些过滤必须留下处置记录和健康统计。采集层不得因为“看起来不重要”“没有 @”“主意识没有回复”而静默删除信息；是否产生后续工作由 Router 研判。

## 4. Source 适配器

### 4.1 统一职责

每个 Source 适配器只负责：

1. 从权威来源取得事件。
2. 给出稳定的来源身份和去重键。
3. 保留原文、附件或可靠原始引用。
4. 把事件归入一个或多个 Thread。
5. 提供来源时间、作者、可见性和关联信息。
6. 在 Observation 持久化成功后推进自己的采集位置。

适配器不负责决定重要性、创建潜意识任务、唤醒专业 Session 或替 Router 作出语义判断。

### 4.2 两类入口

- **主意识投影适配器**：从主意识耐久事件记录中提取实际输入、输出、工具结果和回执。
- **独立来源适配器**：邮件等来源可以直接形成 Observation，不要求先伪装成主意识消息。

如果一份邮件尚未交给主意识，就不能标记为 `into_conscious`。`被潜意识收到`、`被主意识收到`和`被主意识回复`必须分别可证。

### 4.3 多来源身份

不能再用单一 `event_seq` 或单一 `source_cursor` 表示所有来源。至少区分：

```text
source.kind       来源类型，例如 conscious_session、email
source.instance   哪个具体来源配置
source.eventId    来源内部稳定事件 ID
source.cursor     该来源自己的恢复位置，按 instance 分开保存
```

同一来源身份重复出现而内容哈希不同，应报告来源冲突，不能悄悄覆盖旧观察。

## 5. SurfaceObservation：权威观察记录

### 5.1 含义

Observation 是不可变事实记录，只证明某份信息在某个边界被收到或产生。它不自动证明：

- 内容真实；
- 信息重要；
- 已形成记忆；
- Router 已经看过；
- 某项工作已经获得授权。

### 5.2 最小记录契约

以下是逻辑契约，不规定最终数据库列或 TypeScript 文件名：

```ts
interface SurfaceObservation {
  observationId: string
  source: {
    kind: string
    instance: string
    eventId: string
  }
  ingestSeq: number
  occurredAt: string
  recordedAt: string
  kind: string
  actor?: string
  threadRefs: string[]
  consciousSessionId?: string
  payloadRef: string
  contentHash: string
  modalities: string[]
  correlationRefs: string[]
  visibilityRef: string
}
```

约束：

- `observationId` 稳定，重试和重启不改变。
- `ingestSeq` 由潜意识宿主分配，提供全局接收顺序。
- `occurredAt` 是来源声称的发生时间，`recordedAt` 是宿主实际保存时间，两者不得混用。
- `consciousSessionId` 只在确实关联主意识 Session 时出现。
- 原始正文或附件不能被后续 Decision 改写。
- `visibilityRef` 保留私聊、群聊、用户和来源的权限边界。

### 5.3 原文、附件与投影

- 小型正文可以随 Observation 保存。
- 大型正文、图片、语音和文件优先保存可靠附件引用、内容哈希和授权续读方式。
- 权威原文不得被摘要替代。
- 摘要、文本截断和模态转换都是派生投影，必须能回到原 Observation。

## 6. Thread 与关联管理

### 6.1 Thread 的职责

Thread 管理同一来源会话或话题内的事件顺序，为 Router 提供连续上下文。Source 负责定义哪些 Observation 属于同一 Thread。

例如：

```text
kook:<instance>:direct:<user id>
email:<instance>:thread:<message thread id>
conscious:<session id>:<surface thread>
```

具体格式由适配器拥有，Router 不自行猜测平台会话结构。

### 6.2 Correlation 的职责

Correlation 只连接相关证据，例如：

- 外部消息 → 主意识输入；
- 主意识决定 → `send_text` 工具调用；
- 工具调用 → 渠道回执；
- 潜意识任务 → 形成它的观察。

关联不自动改变路由，不自动扩大读取权限，也不证明跨来源因果。

### 6.3 顺序

- Batch 内的全局排列以 `ingestSeq` 为准。
- Thread 内优先使用来源顺序；只有来源时间时必须保留并列、乱序和时钟异常的处理依据。
- 不同平台时间接近不代表它们存在因果关系。

## 7. 待研判队列与 Observation 生命周期

Observation 可以拥有“是否仍等待首次 Router 研判”的队列标记，但这个标记只服务于调度。

必须避免以下等价关系：

```text
已研判 ≠ 已遗忘
ignore ≠ 删除
closed ≠ 禁止读取
defer ≠ 内容改变
```

一条 Observation 被当前 Batch 忽略后，仍应能够：

- 被 Router 按 ID、Thread 或关联引用续读；
- 被后续 Decision 当作背景证据；
- 被未来任务引用；
- 用于审计“当时为什么产生或没有产生工作”。

如果实现需要 `pending / reviewed` 等工程状态，它们只表示队列进度，不得成为观察内容的可见性开关。

## 8. RouterBatch：一次有界研判视图

### 8.1 保留 Batch 的理由

- 避免每条消息都制造一次模型空调用。
- 让 Router 看到一小段连续经历，而不是完全孤立的消息。
- 为模型输入设置明确预算。
- 为投递、恢复和 Decision 提供稳定审计单位。

### 8.2 Batch 不负责的事情

Batch 不负责：

- 保存唯一一份原文；
- 决定 Observation 永久是否可读；
- 阻止 Router 查询相关历史；
- 把一批无关信息强制归成同一个未来任务；
- 代替后续 Task、Mandate 或 Assignment。

### 8.3 第一版成批规则

建议先使用机械、可解释的规则：

1. 只从尚未获得有效研判的 Observation 中按 `ingestSeq` 取材料。
2. 沿用当前初始预算：每批最多 `20` 条、投影最多 `64 KiB`。
3. 第一条待研判 Observation 到达后开启短暂收集窗口；当前 `2 秒`可作为初始值。
4. 达到条数或字节上限立即截断，多余材料进入后续 Batch。
5. Batch 一旦形成，其成员、顺序和投影哈希不可修改。
6. Router 运行期间新到的信息只进入后续 Batch，不重入当前模型轮。
7. 空队列不调用模型。

第一版先不使用“新消息无限重置安静期”。若实际运行产生过多碎批，再讨论安静窗口，并同时设置最大等待时间，避免持续消息导致永久等待。

### 8.4 延期与重试

- `defer` 保留原 Observation 和原 Batch 的决定记录。
- 到期后创建新的 successor Batch 引用原材料，不改写旧 Batch。
- 技术失败重试沿用稳定投递身份和原始形成轨迹。
- 重试不能把旧信息伪装成刚刚发生的新事件。

### 8.5 一批一个 Decision 的边界

在只有 `ignore / defer` 的最小阶段，可以继续“一批一个 Decision”。但该 Decision 只结束本次研判，不关闭原始 Observation。

未来加入 `dispatch / propose` 后，再单独审定部分材料派发、部分材料延期及多动作事务，不能在本接收文档中提前含糊承诺。

## 9. 向 Router 的实际投递

### 9.1 使用真实长期 Session

Batch 应通过真实 DSH 用户消息进入长期 Router Session，使其成为 Router 自身可恢复的经历，并复用 DSH 的 inbox、串行 AgentLoop、持久化与 Compact。

不建议让 Router 每次只收到“数据库有新数据”的通知，再完全依赖工具主动拉取；那会把实际阅读、可见历史和恢复责任推给不稳定的模型行为。

### 9.2 Batch 消息内容

每条 Batch 消息只包含当前事实：

- 简洁的 `batch_id`；
- 按顺序排列的 Observation 内容；
- 来源、作者、Thread、发生时间和稳定 ID；
- 必要的附件、完整性和续读引用。

稳定操作规则放入 Router 固定提示词，不在每批重复大段工具手册。批次包装不能盖过原始内容，也不能把宿主说明伪装成爱莉的经历。

建议形态：

```text
[subconscious.batch]
batch_id: batch_...
observations: N

[observation/obs_...]
source: ...
thread: ...
occurred_at: ...
<实际内容块>
```

### 9.3 串行与运行中输入

- 同一 Router Session 同时只处理一个当前 Batch。
- 当前 AgentLoop 运行期间到达的新 Observation 继续持久化并形成后续 Batch。
- 后续 Batch 是否通过 DSH inbox 在当前轮结束后接续，由 DSH 真实能力决定；不得自行并发启动第二个 Router。
- 人工控制、任务报告等内部输入以后可以使用明确分类的邮箱，不伪装成表界 Observation。

### 9.4 投递事实

至少区分：

```text
ready             Batch 已形成，等待投递
delivering        正在提交给 Session
session_accepted  用户消息已进入 Session 耐久历史
model_presented   内容实际进入模型请求，有可核对的请求证据
decided           有效 Decision 已持久化
```

如果现有 DSH 接口暂时不能分别证明 `session_accepted` 和 `model_presented`，文档和健康状态必须诚实标明当前只能证明到哪一步，不能用 `whenIdle()` 或一次成功工具调用替代全部证据。

### 9.5 重试与未知结果

- 使用稳定 delivery / request ID 去重。
- 投递结果未知时，先核对 Session 历史和领域存储，再决定是否重发。
- 模型轮结束但没有有效 Decision，Batch 仍是待处理，不得直接视为完成。
- Decision 已保存但后续通知失败时，重试通知，不重复作出决定。

## 10. Router 的续读能力

Batch 是本次阅读重点，不是阅读权限边界。

Router 在自身角色权限内应能读取：

- 当前 Batch 中 Observation 的完整内容；
- 同一 Thread 的前后文；
- 指定 Observation 及其关联记录；
- 既往 Batch 和 Decision；
- 与当前材料有明确关联、且获准读取的历史记录。

任何截断投影必须包含：

```text
complete: false
已呈现范围或缺失原因
稳定 observationId / continuation
```

续读返回仍需遵守角色、可见性域和附件权限，不因为 Router 能接收全量表界流，就把同等权限自动授予专业潜意识 Session。

续读工具的具体名称与 Schema 在工具设计阶段单独审定；本文不声明新增工具已经存在。

## 11. 游标、状态与健康

### 11.1 独立游标

至少区分：

1. **来源采集游标**：每个 Source instance 独立；只有 Observation 耐久保存后推进。
2. **宿主接收顺序**：`ingestSeq`，用于待研判排序。
3. **Session 投递状态**：Batch 是否已进入 Router Session。
4. **模型呈现状态**：是否有真实模型请求证据。
5. **Router 决定状态**：有效 Decision 是否持久化。

任务读取、专业 Assignment 和主动机会呈现各有自己的状态，不能混入上述接收游标。

### 11.2 健康指标

接收系统至少暴露：

- 每个 Source 的启用状态、采集游标、最后成功接收和最后错误；
- Observation 总量、待研判数量和最老等待时间；
- 待投递、投递中、结果未知、待决定和延期 Batch 数量；
- 最近一次实际 Session 接收、模型呈现与 Decision 时间；
- 投影截断、附件缺失、来源冲突和恢复缺口；
- 当前是否休息、是否已有 Router worker、退避次数和下次检查时间。

`空队列`、`休息`、`来源禁用`、`没有新消息`和`故障`必须能区分。

## 12. 故障、休息与恢复

### 12.1 不阻塞主意识

采集应异步执行。Router 模型不可用、专业队列拥塞或 Router 休息时，主意识继续原有工作。

但“不阻塞”不等于“允许丢失”。若 Observation 权威存储失败：

- 不推进对应来源游标；
- 暴露明确健康错误；
- 依靠来源耐久日志或恢复读取补齐；
- 不把游标跳到最新位置维持表面健康。

### 12.2 休息

- 休息期间继续保存表界 Observation。
- 可以暂停新 Batch 投递和模型研判，但不能推进语义完成状态。
- 恢复后按原顺序继续，不重复呈现已经确认的投递。
- 宿主卸载不是休息；卸载回收资源，休息保留持久恢复位置。

### 12.3 存储与容量

权威存储不能因为一次 `ignore` 就删除观察。长期归档、附件清理、隐私删除和容量预算需要独立策略；在策略存在前，不以静默丢弃旧信息解决增长问题。

## 13. 与当前实现的差异

本轮已按本文改造 `@elysia/subconscious`，下表记录代码与隔离测试已经覆盖的范围；正式部署后的真实运行证据仍以运行记录为准。

| 项目 | 已实现范围 |
|---|---|
| 收集范围 | 主意识 `user/message`、可见 `assistant/message`、`tool/call`、`tool/result`；过滤框架上下文与隐藏 reasoning |
| 来源模型 | 统一 `ObservationDraft` / `recordObservation()`；主意识与模拟邮件 Source 共用契约 |
| 游标 | 每个 Source instance 独立游标，另有全局 `ingestSeq` |
| 观察身份 | `source.kind + source.instance + source.eventId` 稳定去重，内容冲突显式报错 |
| Batch | 保留 2 秒 / 20 条 / 64 KiB 初始规则，成员和投影不可变 |
| 读取范围 | 支持完整观察、历史批次、Thread 和全量分页；不受当前 `activeBatchId` 垄断 |
| `ignore` | 只结束本次研判；原观察转为 `reviewed`，仍可读取、追溯和引用 |
| 投递证明 | 分别保存 Session 接收、模型呈现、轮次完成和本批 Decision；无 Decision 的完成轮次会重投 |
| 旧库迁移 | 保留旧表、观察和决定，迁移到新版观察与批次投影表 |
| 外部来源 | 通用入口和模拟邮件测试已完成；真实邮件适配器尚未实施 |

## 14. 接收线的最小实施边界

第一阶段只建立接收本身，不同时实现完整任务系统：

1. 一个通用 Observation 权威存储。
2. 主意识输入与输出的明确采集适配。
3. 每来源独立游标、去重和恢复。
4. Thread 与 Correlation 的最小引用。
5. 有界、不可变 Batch。
6. Router Session 的真实串行投递。
7. `ignore / defer` 只用于结束本次研判。
8. Batch 外合法续读与部分投影标记。
9. 健康状态、休息和重启恢复。

`dispatch`、专业 Session、主动机会和外部发送不在这一阶段验收范围内。

## 15. 验收条件

1. 同一来源事件重复到达只产生一条 Observation；相同身份不同内容会报告冲突。
2. 进程重启后能补齐停机期间的来源事件，不跳过缺口。
3. 一批多条信息保持确定顺序，Batch 形成后成员不变。
4. 达到条数或字节上限时无损拆批，不静默丢弃。
5. Router 运行期间的新消息进入后续 Batch，不发生 Session 重入。
6. 主意识输入、输出、工具调用和回执能够区分并正确关联。
7. `ignore` 后 Observation 仍可读取、追溯和被后续材料引用。
8. Router 可以在权限内续读完整内容和相关 Thread 前后文。
9. 节选和附件缺失具有明确标记，不冒充完整经历。
10. 存储失败时不推进来源游标，也不阻塞主意识正常回复。
11. 休息期间不丢信息，恢复后从原位置继续。
12. 投递结果未知、模型无有效 Decision、通知失败和进程中断都有可恢复状态。
13. 新增一个模拟邮件 Source 时，无需修改 Batch、Router 投递和恢复的核心规则。
14. 私聊、群聊、附件和不同来源的可见性边界不因统一存储而串权。
15. 不向真实 QQ、KOOK、飞书或邮件联系人发送验收测试内容；使用隔离来源和合成事件验证。

## 16. 后续仍需完善

- 真实邮件等独立 Source 的连接器；当前只实现通用入口与模拟邮件验证。
- 渠道后续回执、平台事件与 `pass` 等专门事件类型的更细投影。
- Observation 附件的权威存储位置、引用寿命、隐私删除和跨 Thread 权限策略。
- 主意识普通 assistant 正文与实际渠道 Thread 的更完整关联，不伪造因果。
- 根据真实流量评估 `2 秒 / 20 条 / 64 KiB`，先测量再调整，不引入复杂优先级。
- `dispatch`、专业潜意识 Session、主动机会和任务授权不属于本轮接收线交付。

以上问题不影响先确认本文的核心方向：

> **全量观察、分源游标、完整保存、有界成批、真实 Session 投递、独立研判状态；Batch 管理本次阅读，不垄断信息的生命周期与可见性。**
