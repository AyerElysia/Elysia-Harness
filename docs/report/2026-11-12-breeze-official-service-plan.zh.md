# BreezeTTS2 官方服务迁移计划

日期：2026-11-12（Asia/Shanghai）。状态：迁移前计划与核查快照。服务现已迁移，实际结果见 [迁移验收记录](2026-11-12-breeze-official-service-migration.zh.md)，以下原计划不作为当前运行状态。

目标是将 Spark 的语音推理交还官方 BreezeTTS2 实现，同时保持已有聊天 `send_voice`、直播和旧客户端的调用行为。爱莉现有参考音频及其准确转写不动。计划阶段只更新工程文档；随后执行的服务切换、真实语音与用户确认均在迁移验收记录中。

## 1 采用官方服务的边界

用户指定的官方仓库已提供实时音频流生成与 HTTP 服务，无需我们重写推理程序。当前核对的上游版本为 `daa6cb2efe5471f09369229f322d20bb956cb3c3`。后续实施固定到复核过的完整 commit，不以浮动 main 或镜像名称证明版本。

官方负责模型加载、输入准备、采样、流式 codec 解码和 PCM 生成。我们的应用层只负责权限与请求归属、可信音色绑定、共享排队和背压、超时取消传播、文件格式包装及平台投递；不得导入模型张量、重写 token 循环或修改官方推理源码。

上一轮答复核查的是本地接口，没有充分区分官方服务与本地 fork。此处明确更正：官方本来就支持实时音频流；完整文字输入与音频输出流是两个不同维度，不能把“没有增量文字追加接口”说成“没有实时生成能力”。[S1][S2]

## 3 官方接口与兼容风险

固定版本提供 `POST /v1/audio/speech`，接收完整 Form 文本与可选表达、参考及采样字段，响应 mono PCM 流。没有同一请求持续追加文字的接口。单推理槽忙时返回 409；无我们当前的共享 FIFO 或私有任务取消端点。[S2]

官方 `/health` 已包含 `status=ok` 和 `sample_rate`，可满足旧 Python 探针的这两个核心条件；仍需真实连通验证，不能误报这两项本身不兼容。现有扩展 ready/busy/queued 不属于该官方响应。官方 `/v1/model` 提供模型 digest 与限制，但 digest 不覆盖参考音频、全部音频 tokenizer 资产和依赖，发布清单需另外绑定这些内容。[S2]

断连后官方负责关闭流并等待正在执行的生成步骤清理，不能假定客户端 abort 就立即释放 GPU。批量接口与流式接口共用资源，本阶段普通聊天不改走 batch；批量不是实时通话的替代。[S2]

## 4 服务结构建议

```text
聊天 send_voice ──→ 保留的完整 PCM 转 WAV ──┐
直播 requestBreeze ──→ 保留完整音频契约 ───┼→ 轻量共享接入层 → 官方 Breeze API → 官方推理
旧 Python TTS ────────────────────────────┘        │
                                                └→ 状态与有界调度
未来通话 ──→ 新增 PCM 流消费接口 ────────────────┘
```

建议继续由 `127.0.0.1:7862` 提供现有调用入口，官方后端位于私有网络地址。具体内部地址、端口及 owner 在实施前核对，不预占未知端口。接入层必须是独立的协议与资源管理边界，不是另一份推理服务。

之所以保留薄接入层：现有 Node 客户端遇 409 即失败，旧 Python 只做短暂有限重试。若所有消费者直接并发请求官方单槽服务，聊天就可能因忙碌丢失合成机会。这里选择显式、有界共享调度，不要求模型工具修改参数或感知推理后端细节。

接入层应满足：

- 只有一个全局推理槽 owner，覆盖聊天、直播和旧客户端；排队及容量透明，先保持 FIFO，不按内容、平台或“语音更重要”自动抢占。
- 先保留现行技术预算作为兼容基线并配置化；预算耗尽明确失败，不无限重试、无限堆积或生成半条成功音频。
- 保留 `X-Breeze-Client` 与 `X-Breeze-Timeout-Ms` 的兼容处理，但它们不是鉴权。未知扩展字段不得被假称为官方能力。
- 排队请求可在本地移除；在途请求通过关闭官方流传播取消，清理确认前不能把推理槽发给下一任务。若仍遇 409，需有界等待或明确失败，不回改官方锁实现。
- 明确状态：等待、准备、接收 PCM、清理、完成、失败和结果未知；不能用排队成功或 HTTP 建连成功表示合成完成。
- 兼容层若返回扩展状态，应区分应用调度状态和官方后端健康；不能让旧 UI 把兼容层 ready 当作模型已加载。
- 仅内部受控调用可达，不额外暴露公网推理、取消或参考资产接口。日志只记录必要 ID、阶段、字节数和错误码，不记录私人正文、参考转写、音频或凭据。

如果实施中能证明所有当前消费者已有同一个共享调度 owner，可复用它而不再增加常驻接入进程；不能用多个调用端各自排队冒充全局调度。无论载体为何，推理代码保持官方不改是硬边界。

## 5 聊天和直播保持不变

以下为迁移验收条件，不是本轮已完成的真实发送证明。

| 调用契约 | 必须保持 |
|---|---|
| 模型工具 | `send_voice(channel, conversation, text, expression_instruction?)`，无需模型学新参数 |
| 固定音色 | 仅从可信配置取 default；参考音频字节、路径、准确转写和基础 instruction 不变；模型无替换入口 |
| 表达控制 | 现有自然语言表达指令及 `[笑]`、`[叹气]` 等按原样传递，不由关键词规则代选情绪 |
| HTTP 输入 | multipart `text/instruction/cfg_scale/ref_text/seed/ref_audio` |
| 音频协议 | `audio/pcm`、`X-Sample-Format: s16le`、有效 `X-Sample-Rate`；不得无条件改成 SSE、JSON 或 MP3 |
| 普通语音消息 | 收齐 PCM 后封装单声道 WAV，完整成功后才进行一次平台投递 |
| 超时和取消 | 总预算覆盖排队、请求和读流；失败不返回部分 WAV，取消不继续发送 |
| 投递结果 | 保留 `sent/synthesis-failed/send-failed/unknown`；未知投递不自动重发 |
| 直播 | `requestBreeze()` 的完整 WAV、真实音频总长与既有时间线接口不变 |
| 渠道边界 | 本次只确认 KOOK 登记 OutboundVoice；不把其他渠道尚未实现的语音能力列为迁移成功 |

官方 Voice Direction 在参考音频下控制表达，不必切 Voice Design 或换声线。[S1] 参考固定只保证资产未被替换，听感仍需人工对比；升级推理版本后不能要求整个输出 WAV 与旧实现逐字节相同。

## 6 迁移顺序和放行条件

### 第一步 固定旧基线与发布清单

留存现行容器配置的必要非敏感字段、image id、源码 commit、依赖版本、启动入口、权重和音频 tokenizer 版本。对参考音频和转写作受保护的哈希校验，不复制正文进公共报告；不能因迁移而转码、降噪或重剪参考音频。

从现有已授权的测试会话收集正常语音样例、表达样例及发送回执；真实发送目标需经任务授权。本轮没有发出这些测试。保留旧部署可回滚，不 reset 本地 fork，也不删除权重、声音数据或历史。

放行条件：旧版本与调用行为可复现，固定音色资产可校验，测试目标和切换 owner 明确。

### 第二步 验证纯官方后端

仅从固定官方 commit 构建可复现产物，不携带本地 `service.py`、改写的 API 或 `fast_streaming.py`。先验证官方 eager 流式基线，再逐项评估 fast flags。官方 Dockerfile 默认是 H100/Hopper 方向，不能原样视为 GB10/Arm64 兼容；允许适配基础镜像、依赖版本和构建方式，不允许借适配硬件继续改写采样与解码。[S3][S4]

只在已核对内存、现存推理任务和 GPU 预算后安排真实模型测试；不能在现有服务旁直接并发拉起第二个模型再声称隔离。必要时安排明确的 TTS 测试窗口，不重启主意识或平台连接。

验证 `/health`、`/v1/model`、模型与依赖清单、PCM 首块/结束、音色、表达及断连后下一请求可用。官方 H100 延迟指标不作为 Spark 承诺。

放行条件：纯官方源码身份、Spark 可运行性及基础音频行为都有证据；未通过则不切生产。

### 第三步 先验兼容与故障

通过接入层对 Node 聊天、直播及旧 Python 运行契约回归，覆盖三者竞争、有界等待、容量耗尽、排队取消、等头取消、读 PCM 取消、后端 409/503、清理未完成和总超时。官方健康字段能兼容的直接保留，不制造无意义转换。

平台发送阶段区分合成失败、上传失败、明确发送失败与结果未知。KOOK 原生语音只在现有明确错误条件下回退文件消息，不能扩大为遇错都重发。

放行条件：不重复、不串音、不把失败视为成功，不破坏完整音频契约；流式取消后资源释放可证明。

### 第四步 排空后切换并真实验证

先暂停接入新合成、排空在途任务，确认旧进程不再持有推理槽，再在受控窗口切换端点。等待中的请求必须保留其身份与截止时间，不能静默丢弃；无法满足预算的请求明确失败。切换窗口不承诺零中断。

切换后从已授权聊天目标实际调用一次 `send_voice`，验证收件端可播放、只有一条消息、音色正确，再测表达控制、直播与旧消费者。为每项记录合成、发送、播放证据，平台不提供播放事实时明确边界。

放行条件：普通聊天、直播和旧消费者的真实验收通过，参考哈希不变，错误处理与延迟未出现不可接受退化。门槛由实施前的基线和用户可接受范围确定，不用 H100 宣传数字替代。

### 第五步 停用本地推理改写

验收后从活跃部署移除旧本地推理 fork、旧 worker 挂载与无效路径；在版本历史与受控回滚资料中保留准确版本。不得递归删除模型、参考声音、原始数据或主体文件。

明确单一启动、停止、状态和日志入口，状态应显示实际官方 commit、模型清单、后端健康、队列和最后错误。运行策略单独确认，不给 Elysium 增加自动启动或隐式重拉。

放行条件：运行时确实只加载官方推理实现，旧代码不在导入路径，不是仅改了容器标签。

## 8 回滚和本轮边界

官方后端不就绪、音色漂移、取消后槽不释放、聊天投递失败或兼容异常时，停止新切换并明确报告，恢复此前留存的端点和部署。恢复前后都需排空或明确结束归属任务，未知投递不得重新发送。回滚是显式工程操作，不是运行时静默切换或故障无限重启。

计划阶段执行：公开上游代码核对；Spark git/容器挂载/端口/硬件的只读检查；GET health 和 model 查询；更新本计划与通话需求中的声音决定。未安装依赖、构建或拉取镜像、运行 TTS/模型、发送消息、改代码/配置、重启服务或触碰依赖锁。后续实施步骤与回归测试均未执行。

未来 Realtime 通话只作为下一阶段消费者，另增 PCM 流消费接口，不把现有聊天 `requestBreeze()` 改成半条音频流。本轮不接 Realtime，也不使用聊天中出现过的 API 密钥。
